# BLITZ values

BLITZ should make a mixed fleet of robotics computers feel like one deployable
system. These values guide implementation, review, and future agent decisions.
They describe the intended design; existing behavior can still need correction.
Read them alongside [AGENTS.md](AGENTS.md) and the
[architecture guide](docs/deployment-architecture.md).

## 1. Discover endpoints; collect one catalog

**mDNS locates machines and their service endpoints; the watchdog's HTTP catalog
is the source of deployment specifications.** Keep mDNS announcements lightweight:
identity, addresses, service ports, and the protocol version. Architecture, OS,
runtime details, and capabilities belong in one versioned catalog generated by
the watchdog, not in separate sources of device truth. The watchdog and client share one typed
catalog schema, with native JSON capability objects.

Finish endpoint discovery first, apply hostname/IP blacklists, then fetch one
catalog per allowed machine in a single collection phase. Build, transfer, and
process assignment reuse that in-memory result. Known addresses, including
Docker simulations, enter the same filtering and HTTP collection path. Missing
or invalid catalogs must stop deployment clearly rather than produce a partial
fleet or trigger an unrequested discovery fallback.

Keep live identities, addresses, and port mappings out of persistent inventory.
Remember only distinct build profiles needed for offline dependency caching;
never use remembered profiles as deployment destinations. Users should be able
to switch devices without editing a saved device list.

## 2. Bundle everything compatible

**Every target bundle includes every compatible module declared by the project.**
Process placement decides what starts on a device; it must not reduce what goes
into that device's bundle. Libraries, programs, resources, and their required
dependencies belong in the bundle even when a program is assigned elsewhere.

For example, a fleet has an Intel/x86 computer, an ARM computer, and a Jetson Nano.
The project declares ordinary portable modules and a CUDA-only module:

| Target | Ordinary modules | CUDA-only module |
| --- | --- | --- |
| Intel/x86 computer without CUDA | Include, built for x86 | Exclude |
| ARM computer without CUDA | Include, built for ARM | Exclude |
| Jetson Nano with compatible CUDA support | Include, built for its architecture | Include |

These are the same ordinary modules compiled or packaged separately for each
target, rather than identical native binaries copied across architectures.
CUDA support must satisfy the module's actual requirements; a product name or
CPU architecture alone is insufficient evidence.

Exclude a module only for an explicit compatibility reason, including an
incompatible required dependency. Explain every exclusion and its dependency
chain. A compilation failure is an error, not permission to silently omit a
module. Reject process assignments that require an excluded module.

## 3. Model the target in one build environment

Generate one reusable Dockerfile and build context per distinct discovered
system profile. Devices with the same complete profile may share that context.
Match the target's architecture, distribution, runtime ABI, and relevant hardware
capabilities as closely as possible. Do not create separate competing Python,
C++, and Rust environments for the same system.

Keep provisioning and compilation in the predefined build script, driven by a
generated plan. The Dockerfile assembles the environment and invokes that script;
it should not grow its own inline dependency-installation logic.

## 4. Deliver artifacts, not a Docker runtime

Docker runs on the build machine to produce target-compatible executables,
libraries, Python dependencies, and assets. The device receives and runs the
bundle. It must not need to run the build image or compile project code itself.
Package Python dependencies for offline installation, including dependencies
that need native compilation.

## 5. Prepare online; build and deploy offline

When deployment finds missing dependency caches, check for internet access on
the build computer and attempt to prepare the missing caches if it is detected.
Keep the separate online `cache` command for preparation ahead of deployment;
it is optional when internet access is available during deployment.
Build from cached dependencies without network access, and install the bundle
without internet access on the device. Failed preparation must stop before
building or transferring. Without detected internet access, stop with clear
next steps unless the user explicitly accepts a cached stale dependency image.
Any use of stale dependencies must never bypass target compatibility checks.

## 6. Cache by what affects compatibility

Include system characteristics and dependency inputs in cache identity. Source,
entrypoint, generated-file, and resource edits rebuild the bundle without
unnecessarily downloading dependencies again. Reuse caches across equivalent
targets; keep device identity and deployment destination separate from build
compatibility.

## 7. Keep project declarations small and typed

Projects declare modules, dependencies, target requirements, configuration, and
process placement. BLITZ owns discovery, build orchestration, transfer, and
runtime setup. Avoid making applications duplicate BLITZ infrastructure or
replace internal functions to accomplish normal deployment.

Preserve `get_modules()` and `pi_name_to_process_types()`. Prefer
`BackendModules(__file__)`, `SupportedModules`, `ProcessPlan`, and
`WeightedProcess` over manual paths and new ad hoc configuration formats.
Resolve project paths independently of the caller's working directory.

## 8. One module owns one complete folder

Keep each module and its assets under `backend/<language>/<module-folder>` or
the configured installer backend root. Do not split files from one folder into
multiple module declarations. Put shared source in the language's `common/`
folder and portable generated assets in `backend/generated/`.

Do not expose sibling Python modules as import paths. Native dependencies cross
module boundaries through declared compiled exports. Keep one root Python
`requirements.txt` and one target virtual environment; retain existing language
dependency conventions unless deliberately replacing them.

## 9. Make dependencies and compatibility explicit

Use declared module IDs and target requirements to build an ordered dependency
graph. Reject duplicate IDs, unknown dependencies, cycles, missing outputs, and
unresolved native libraries. Unknown hardware capabilities do not count as
available. Keep platform-specific build decisions in compilation adapters.

Use an official capability registry with defined meanings, value types, and
detectors. Distribution/build profiles select relevant detector families; they
do not prove that hardware exists. A family can report multiple related
capabilities from one probe. Advertise only verified, accessible support, and
reject unsupported capability names or meaningless version requirements.

Cache expensive system and capability collection inside the watchdog and refresh
on a configurable interval. Advertising mDNS or serving repeated HTTP requests
must not rerun those probes every tick. Both real and simulated watchdogs use
the same catalog logic; simulations configure reachable endpoints rather than
forking installation or process management.

Package and expose each program's transitive dependencies consistently at build
time and runtime. Isolate independent library providers, and reject conflicting
libraries within one program's dependency closure instead of depending on search
order or the development machine's environment.

## 10. Run ordinary programs predictably

Programs should not need a custom BLITZ argument parser. Supply configuration
and runtime paths through stable environment variables, use explicit entrypoints
and working directories, and pass arguments as argument lists. Keep legacy
BLITZ flags opt-in. Distinguish module identity from runnable process identity.

Run the watchdog, ordinary programs, and post-provisioning application checks as
the configured non-root device user. That user owns the deployable runtime tree,
including Python bytecode caches. Discovery helpers read the watchdog API rather
than importing target code as root. Bundle replacement must not silently escalate
permissions to hide incorrect provisioning or runtime ownership.

## 11. Keep deployment scope explicit

Use the selected device records consistently across every deployment phase.
An empty or invalid selection must fail clearly; it must never silently expand
to the entire fleet. Simulation and physical deployment must not accidentally
share destinations. Offline inventory describes remembered systems, not proof
that a device is currently reachable or selected for deployment.

Simulation is an explicit, off-by-default mode configured in the deployment
script. Its known watchdog endpoints use the same catalog flow and never fall
back to physical discovery. Optional fleet expectations check the exact allowed
device count and distinct deployment profiles before any build or transfer.
Reject missing, extra, or incompatible devices clearly; do not silently select
an arbitrary subset or count one device toward multiple required profile slots.

## 12. Explain failures and preserve trust

Report the failing target, phase, module or step, reason, and useful log location.
Validate incompatibilities and invalid process plans before compilation or
transfer wherever possible. Do not claim success after silently dropping work.

Preserve unrelated repository and application work, including installed project
deployment declarations. Keep local Python and installer/Gradle workflows
compatible unless explicitly replacing them. Never commit secrets, machine
identities, caches, or build artifacts. Generate protobuf code from its source
definitions rather than editing generated files.

For behavior changes, run the required validation and bump the deployment build
version according to [AGENTS.md](AGENTS.md). Documentation alone needs no bump.

## Review questions

- Does discovery finish and apply blacklists before collecting HTTP catalogs?
- Is the live device list ephemeral, with only build profiles saved offline?
- Are capabilities registered, verified, grouped, and refreshed periodically?
- Does each bundle contain all compatible modules, independent of placement?
- Are exclusions explicit, dependency-aware, and explained?
- Does one target environment produce a bundle that works offline?
- Can an application use this through the public typed APIs without workarounds?
- Are target selection, compatibility, cache reuse, and failures predictable?

When implementation conflicts with these values, identify the conflict and
address it directly. Update these values only when the intended design changes;
do not weaken them merely to describe a regression.
